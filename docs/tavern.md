# 酒馆后台与微信小程序（第一版）

当前范围是酒单与配方维护、自然语言推荐、购物车和基于已完成订单推测的“老样子”。不创建订单、不接收付款；本地 mock 使用明确标注的虚构订单演示推测过程，服务端不自动填入演示消费记录。现有文档、问答和审查功能保留。

## 使用流程

当前小程序默认以所选 **01 深夜唱片酒馆** 风格运行本地 mock，无需启动后端。浏览器可先打开 `http://127.0.0.1:5173/bar`，具体见 [主界面设计与 mock 说明](bar-concepts.md)。以下后台联调流程需先把 `miniprogram/config.js` 的 `mockMode` 改为 `false`。

1. 按 README 启动服务，管理员登录后进入侧栏 **酒单与配方**。
2. 点击 **下载模板**，用自己的酒单替换示例，再点击 **导入酒单**；也可以逐款新增。模板为 [虚构演示酒单](../examples/tavern-menu.json)，不会自动写入已有数据库。
3. 核实每款酒的售价、酒精度、甜度、公开原料、过敏原和风味标签，再上架。内部配方填写用量和制作步骤，不会返回到顾客接口。
4. 微信开发者工具导入仓库下 `miniprogram/`，将 `project.config.json` 的占位 `touristappid` 换为自己的有效小程序 AppID（当前工具提示游客 AppID 不受支持）。AppSecret 不放进小程序。
5. 在 `miniprogram/config.js` 设置后端 API 地址，保留末尾 `/api`。本机开发默认 `http://127.0.0.1:8000/api`，仅适用于本机模拟器；真机的 127.0.0.1 不指向电脑。
6. 本地模拟器调试 HTTP 地址时，在开发者工具的本地设置中暂时关闭域名校验；该设置只留在被 Git 忽略的 `project.private.config.json`。正式环境使用 HTTPS，并在微信公众平台设置 request 合法域名。

原始 PDF / DOCX / Markdown / TXT 配方资料仍可以上传到 **知识文档**，敏感配方选择仅管理员可见。当前不会自动把非结构化文档变成上架酒单；需按模板录入并人工核实可售字段。顾客推荐只读取结构化酒单，不调用内部知识问答接口。

## 小程序三页

- **今晚**：摄影封面、纸质调酒师便签、鸡尾酒/精酿分类和固定输入框。输入“给我一杯微甜的无酒精鸡尾酒”，继续说“40 元以内”，从推荐结果加入杯垫。“重新聊聊”会让下一轮从新需求开始。
- **我的杯垫**：购物车的场景化名称。增加、减少、移除酒款，显示当前有效酒款合计；加入或修改杯垫不构成已完成订单。下架或不符合新偏好的酒款显示失效并不计价，不会偷偷替换。
- **我的口味**：保存只看无酒精、忌口和过敏原，展示参与推测的历史订单笔数。偏好由服务器按顾客身份持久化。

“老样子”由 Agent 根据服务端当前顾客的已完成订单推测，不需要顾客手动保存。当前实现先采用可解释的统计规则：近 90 天最多 10 笔有效已完成订单，同一酒款至少出现 3 次且占比不少于 60%，频次不能并列第一；通常杯数取出现次数最多的数量，数量频次并列时采用最近一次。取消和整单退款不计入，部分退款扣除已退款杯数。历史不足或偏好分散时追问，不擅自确定。

推荐展示“最近 5 笔已完成订单中点了 4 次，通常 1 杯”等依据；顾客确认后才加入杯垫，推荐本身不会修改杯垫。当前无酒精、预算、忌口等要求始终优先，常喝酒款下架或不符合要求时不冒称其他酒款是老样子。浏览器 mock 支持查看虚构演示订单；浏览器与原生 mock 使用同一份虚构订单 fixture，均为规则推测，尚未接入真实订单系统或大模型消费习惯分析。

购物车和偏好使用修订号防止多窗口覆盖；发生冲突时保留当前显示并提示刷新，不会自动重试导致数量翻倍。购物车只保存酒款 ID 和数量，单价、总价、上架状态由服务端计算；第一版的合计不是锁价或订单金额。

## 推荐与真实配置

`DEMO_MODE=true`：关键词解析与规则筛选，不调用模型。支持无酒精、微甜、不甜、甜口、数字预算、已知原料忌口、常见过敏原和“老样子”；任意口语理解不在此模式的保证范围内。演示登录为每次新登录生成独立顾客，令牌本地保存，最长 30 天；清除缓存或令牌过期后不会自动找回原演示身份。

`DEMO_MODE=false`：复用服务端聊天模型配置，将当次需求和上一轮结构化条件交给模型解析为受约束的 JSON；服务器再使用酒单筛选，模型不能创造 SKU、售价、配方或直接执行购物车动作。明确的无酒精、甜度、预算及已识别忌口条件不能被模型放宽；持久化偏好也不会被聊天覆盖。解析失败、截断或返回无效 JSON 时提示重试，不当作推荐完成。

无酒精仅匹配明确标注 `alcohol_percent: 0` 的酒款。`sweetness` 为 0–4 的口感分级，不代表糖含量；“无糖”需要店员核实。过敏筛选使用门店公开原料与过敏原字段及常见别名，不能代替原料检查和制作环境确认。

正式微信登录额外在后端本地 `.env` 配置：

```dotenv
WECHAT_APP_ID=wx你的AppID
WECHAT_APP_SECRET=仅在本地填写
```

后端用 `wx.login` 返回的一次性 code 调微信 `jscode2session`，只使用微信服务器返回的 OpenID 关联顾客。前端不能提交 OpenID 或角色。正式模式禁止演示顾客登录。后台 Cookie 与顾客 Bearer 令牌使用不同签名用途；顾客身份不能读取文档、内部配方或其他顾客的购物车、偏好和订单推测结果。

真实模型模式会向配置的模型服务发送顾客当次需求与上一轮结构化口味条件，不发送内部配方或微信身份。上线前需提供相应隐私说明，并在真实环境验收模型、微信登录和 HTTPS 域名；本次不包含发布、支付、库存扣减、制作单或多门店。

## 主要接口

| 接口 | 身份 | 用途 |
|---|---|---|
| `GET /api/admin/tavern/drinks?q=&page=1` | 后台管理员 | 酒单搜索、分页、内部配方 |
| `POST /api/admin/tavern/drinks` | 后台管理员 | 新增酒款 |
| `PUT /api/admin/tavern/drinks/{id}` | 后台管理员 | 按 revision 编辑或上下架 |
| `GET /api/admin/tavern/template` | 后台管理员 | 下载 JSON 模板 |
| `POST /api/admin/tavern/import` | 后台管理员 | 整批事务新增；重复时不覆盖 |
| `GET /api/tavern/config` | 公开 | 演示状态；checkout_enabled 恒为 false |
| `POST /api/tavern/login` | 公开 | demo 或 wechat 登录，返回顾客令牌 |
| `GET /api/tavern/menu` | 顾客 | 按偏好过滤的公开在售酒单 |
| `POST /api/tavern/recommend` | 顾客 | message、reset；返回推荐、数量与 usual_inference 推测依据 |
| `GET /api/tavern/me` | 顾客 | 偏好、参与推测的订单笔数、推测来源、revision |
| `PUT /api/tavern/preferences` | 顾客 | 按 revision 保存偏好 |
| `GET /api/tavern/cart` | 顾客 | 当前价格、有效状态与合计 |
| `PUT /api/tavern/cart` | 顾客 | items 与 revision；替换待选清单 |

新增 `tavern_drinks`、`tavern_customers` 与 `tavern_order_records` 独立表，通过现有初始化流程创建，不迁移或删除旧文档和会话。`tavern_order_records` 是可信订单系统的只读历史适配表，目前尚待接入真实来源；没有订单创建、历史写入或支付接口，客户端不能提交订单历史或指定其他顾客。旧 `usual` 数据字段仅为数据库兼容保留，不参与推测。正式环境仍需常规备份。

## 验证

```bash
bash scripts/check.sh
# 启动使用独立演示数据库的服务后：
cd frontend && npm run test:e2e
# 在仓库根目录运行原生页面逻辑与真实演示 API 的联调：
node --test scripts/test-miniprogram.cjs
```

`check.sh` 包含小程序 JS / JSON 检查；macOS 本机装有默认路径的微信开发者工具时，会额外调用 WXML / WXSS 编译器。原生页面联调脚本验证需求推荐、购物车数量、历史不足提示、忌口、多页面冲突和失败恢复；Python 隔离测试验证历史推测、顾客隔离、退款过滤及当前条件优先，但不替代微信模拟器界面验收。微信协议和模型测试使用 mock 时，只表示协议与校验逻辑通过，不代表真实平台已联通。
