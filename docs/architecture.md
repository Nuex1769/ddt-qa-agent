# 架构与运行边界

## 入库

登录管理员 → 文件类型和大小检查 → 提取文字 → LlamaIndex SentenceSplitter（650 字符、100 字符重叠）→ 混合检索模式批量向量化 → 事务写入文档与片段。

文字文件使用 UTF-8；PDF 提取包含页码文本，最多 1000 页，暂不进行 OCR；DOCX 提取段落和表格。单文档最多提取 200 万字符。上传时同步等待索引成功，前端显示进度并防止重复提交，不依赖后台队列。更新失败保留旧文档。

## 检索

身份与部门权限 + 产品/版本 → BM25 关键词检索 → 可选向量召回 → RRF 排序 → Top K（默认 5）→ 有编号的上下文 → 流式模型生成。

`RETRIEVAL_MODE=keyword` 不访问向量服务，适合先用 DeepSeek Flash 跑通真实问答；`hybrid` 使用独立可配置的向量服务。演示模式始终只使用本地关键词检索。配置指纹仅包含向量服务地址、模型与维度，避免混用不兼容向量，也不因聊天配置变化而失效。

PostgreSQL 通过 pgvector 余弦距离查询向量，创建 HNSW 索引。SQLite 在混合检索模式下也能保存 JSON 向量并计算余弦相似度，供小规模本地验证。

当前 BM25 为进程内计算：会读取当前用户可访问范围的片段，适合第一版小到中等资料集。大量文档、高并发部署应迁移至独立全文检索/持久化 BM25 索引、异步入库队列和连接池调优，尚未做大规模负载测试。

当前采用固定 RAG 流程，没有多 Agent 调度、自主工具执行、长期个人记忆或微调。会话历史仅用于理解上下文，不作为产品事实依据。

## 流式协议

`POST /api/chat` 请求示例：

```json
{"question":"知识库支持哪些格式？","conversation_id":null,"product":"DDT 工作台","version":"v2.4"}
```

响应为 `text/event-stream`：

| 事件 | 数据 | 含义 |
|---|---|---|
| conversation | `{ "id": "…" }` | 新建或继续的会话 |
| status | `{ "message": "…" }` | 检索/生成状态 |
| sources | `{ "items": [...] }` | 有权访问的引用片段 |
| delta | `{ "text": "…" }` | UTF-8 增量正文 |
| done | `{ "message_id": "…", "conversation_id": "…" }` | 完成并已保存 |
| error | `{ "message": "…" }` | 失败，不能视为完成 |

前端使用 `fetch` 读取 POST 响应；TextDecoder 流式解码并按 SSE 空行分隔组装，不把网络分块当作事件。缺少 `done` 视为断流。`AbortController` 停止生成，服务端检测取消并在 finally 保存已生成内容，标记 interrupted。单轮生成总时限 240 秒，同会话使用数据库原子租约避免并发生成，租约最长 300 秒。

模型流必须提供文本 delta 和 `finish_reason=stop`。内容过滤、输出截断、空回复及提前断流会触发 error，前端保留部分内容并提示重试。未启用自动重试，避免重复计费。

DeepSeek 官方使用 `https://api.deepseek.com/chat/completions`、模型 ID `deepseek-flash`。`CHAT_THINKING=auto` 对官方域名默认关闭思考，可显式开启；仅把 `delta.content` 推送给前端和保存，忽略 `reasoning_content` 及用量帧。没有配置独立向量服务时，不将官方聊天服务作为默认 Embedding 接口。

## 权限与历史

后端从签名 HttpOnly Cookie 取得用户身份，再从数据库读取当前角色与部门，客户端不能自行声明管理员身份。普通成员可访问全公司文档、本部门资料及自己拥有的文档；管理员可管理全部文档。会话严格绑定所有者。

引用保存文档 ID、摘要、修订时间与当时的片段。历史消息读取时重新校验访问权限和修订版本；有任何引用失效，就隐藏该旧回答和其引用。更新/删除文档不会把失效的历史内容继续交给模型作为上下文。

文档中的提示词可能不可信，系统指令会声明仅把参考资料视为数据。界面不执行原文 HTML，不自动加载 Markdown 中的远程图片，避免资料内容引起外部资源请求。但当前版本没有独立提示词注入检测、DLP 或人工审批系统。

## 观测记录与 Langfuse

`observations` 保存问答、审查的无正文运行记录；管理员接口位于 `/api/observability`。使用 ContextVar 隔离并发请求的 trace/span，在检索、模型生成、审查及向量调用处采集耗时和模型返回用量。调用完成、失败或取消后保存状态，生成器在原上下文中显式关闭以保证 span 正确结束。

可选 Langfuse 同步使用持久状态、退避重试、原子领取租约及 OTLP/HTTP JSON 后台上报，与主业务流分离。详情跳转、上报范围和部署配置见 [Langfuse 说明](langfuse.md)。

## 文档审查、草稿和版本

`documents` 和 `chunks` 始终保存当前已发布内容。新增 `document_reviews`、`review_turns` 和 `document_versions` 表保存独立审查记录、草稿、发布快照和采用建议的来源，不在检索查询中混入草稿。现有数据库通过新增表和当前版本快照回填升级，不删除已有资料。

审查对话绑定用户、文档 ID 和目标修订时间。目标正文每 12000 字符一段，检索其他文档时复用 `visible_documents` 过滤并排除目标文档，再按文本关联度筛选；没有相关资料时只审查目标。正式模型返回结构化总结与建议，服务端校验建议种类、原文是否精确唯一、引用编号及可采用条件。内部相关段落作为额外上下文供跨段核对；无法判断资料权威性的问题应交由人工确认。

每一分段完成后先保存结果，再推送 SSE `result`；全部完成并保存状态后才推送 `done`。停止、超时、模型 JSON 无效或截断时保留已完成部分，标记 interrupted/error，并支持从最后完成分段继续。单轮上限 240 秒，数据库租约 300 秒，防止同一对话并发生成。重新读取、继续审查和采用建议时重新校验目标与参考资料权限、摘要和修订，失效时隐藏旧结论。

采用建议仅写入草稿；重叠修改不能再次匹配原文时要求手动合并。草稿保存使用修订时间进行并发校验。版本对比以草稿的基准正文和当前建议稿做逐行差异，确认发布才进行分块、向量化（如启用）及索引替换。外部索引调用后再次校验管理员权限、来源、目标和草稿修订，再通过条件更新和事务完成发布，失败保留原发布版本与草稿。

修订稿使用 Markdown 保存，不回写原 PDF/DOCX 文件；现有文件导入同样记录发布快照。草稿和历史版本接口限管理员访问，同时校验当前文档权限；审查对话限所有者访问。版本确认由当前管理员完成，尚无多级审批、独立复核人或自动版本回滚。

## 部署边界

- 内置本地账号；没有 SSO、MFA、邀请邮件、自助改密、用户停用管理界面或细粒度权限组。
- 登录频率限制保存在单进程内；默认部署为一个 API 进程，多副本时应使用共享限流与统一会话管理。
- 没有飞书/企业网盘定期同步、OCR、后台任务队列、独立重排模型或质量评测平台。
- 没有自动删除原始会话的保留策略，应按公司要求配置运维策略与备份。
- 模型配置来自环境变量，界面只展示非敏感运行状态，不能在浏览器修改密钥。
- 容器配置已提供；实际模型连通性、PostgreSQL/pgvector 和 Docker 构建需在对应环境单独验收。

首次对团队开放前，应使用真实问题检查回答依据、不同身份权限和产品版本冲突。演示模式用于验证流程，不代表真实模型的答案质量。
